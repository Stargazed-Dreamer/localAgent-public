# team_playbook - 小团队项目启动军规

> 来源：2026-09 一次 game jam 的赛后复盘（10 条原始教训），提炼为通用的多人协作清单。
> 适用于 game jam / hackathon / 课设 / 任何 deadline 紧的多人小项目。
> 游戏专用细则（Godot 窗口大小 / Autoload 单例 / 资产目录）见 godot-ai-toolkit 仓库 `docs/gamejam-lessons.md`。

## 为什么需要

小团队翻车的根因极少是"技术不够"，几乎全是**开工没定标准 + 收尾没留缓冲**。本清单把这两件事固化成军规。

## 开工前 1 小时（最值钱的一小时）

| # | 军规 | 落地做法 |
|---|------|---------|
| 1 | 指定一个 **leader** 定标准、管进度 | 命名规范、常量、目录结构、封包缓冲都由 TA 拍板；不一定要写最多代码，但要敢拍板、盯时间点 |
| 2 | **关键术语统一** | 领域概念（如金钱）一个名字到底，写进共享文档；出现新概念先问"叫什么"再写代码 |
| 3 | **关键数值集中一处** | 全局常量模块 / 配置文件单一来源，禁止各处散落 magic number |
| 4 | **编码风格提前定义** | formatter / linter 配置先进仓库，不靠口头约定 |
| 5 | **目录按功能域分，不按文件类型分** | `player/`、`ui/` 各自内聚（代码+资源放一起），而不是 `src/`、`img/` 各一大堆 |
| 6 | **基础骨架和全局工具先建后铺量** | 开工半小时内由一人建目录骨架 + 全局设施（事件总线 / 数据管理器 / 常量表），避免人人各造一个 |
| 7 | **基础运行参数开工即定** | 游戏 = 窗口分辨率；Web = 断点 / 浏览器基线。不然后期 UI 全返工 |

## 开发中纪律

| # | 军规 | 说明 |
|---|------|------|
| 8 | **先 commit / 保存，再切分支、合并或做任何危险操作，无论如何** | "等会儿再存"是丢代码的第一句话 |

## 收尾：封包 / 发布缓冲

| # | 军规 | 说明 |
|---|------|------|
| 9 | **deadline 前预留打包测试窗口：jam 至少 1 小时，正式项目 1-2 小时，不可妥协** | 功能冻结 → 全员转打包 + 实测。打包必然暴露 bug 和漏掉的文件，这段缓冲是必选项不是优化项；leader 盯时间点 |

## 非技术

| # | 军规 | 说明 |
|---|------|------|
| 10 | **选宽阔的位置坐，周围有沙发更好** | 连续长时间肩并肩作业，工位宽度直接影响心情和效率 |

## 一句话版本

> 开工先定标准（术语 / 常量 / 风格 / 目录 / 全局工具），leader 负责拍板和盯进度；先 commit 再做危险操作；deadline 前留 1-2 小时打包测试，不可妥协。
