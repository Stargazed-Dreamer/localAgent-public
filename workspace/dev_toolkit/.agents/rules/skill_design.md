# Skill 设计规范

> 本文件定义本工具包 skill 的编写规范。创建/修改 skill 前必读。
> 核心理念来自 Anthropic 官方《Lessons from building Claude Code: How we use skills》。

---

## 一、核心认知：skill 是文件夹，不是文件

skill 不是"一份写了步骤的 markdown"，而是一个**装备齐全的工具箱**：

```
my-skill/
├── SKILL.md          # 唯一必需：何时用我 + 操作指引 + 坑点清单
├── references/       # 正文放不下的细节（API 参数、排查手册、背景知识）
├── scripts/          # 现成可执行脚本（冒烟测试、模板生成、校验工具）
└── assets/           # 输出模板（release_note、spec 模板等）
```

- 只有 `SKILL.md` 必需。其余按需添加。
- 子文件**不会**一股脑塞给 agent，而是 SKILL.md 指引 agent "需要时自己去翻"。

---

## 二、触发机制：description 前 250 字符决定一切

agent 决定用不用你的 skill，**唯一依据**是清单里那一行 description。它没读过正文。

### 渐进式披露三层

| 层级 | 何时看到 | 内容 |
|------|---------|------|
| 第 1 层 | 每次会话都看到 | 清单里所有 skill 的 name + description（整张清单只占 context 的 1%） |
| 第 2 层 | skill 被调用时 | SKILL.md 全文 |
| 第 3 层 | 正文指引去读时 | references/scripts/assets 里的文件 |

### description 写法

- ❌ 人类视角摘要："帮助处理数据库相关工作"
- ✅ 模型视角触发条件："当用户要写数据库迁移、修改表结构、或遇到 migration 报错时使用"

**硬约束**：单个 skill 的 description 最多 250 字符，超出被直接截断。装太多 skill 会互相挤占清单预算——**贵精不贵多**。

---

## 三、正文写什么：坑点清单（Gotchas）含金量最高

正文黄金法则：**只写 agent 推断不出来的，删掉它本来就会的。**

### 该写的（信号强）

- **坑点清单 Gotchas**：agent 靠读代码永远推断不出来、只有踩过坑才知道的事。
  - "subscriptions 表是只追加不修改的，要找的记录是 version 最大的那条，不是 created_at 最新的那条"
  - "这个字段在 API 网关叫 @request_id，在计费服务叫 trace_id，是同一个值"
  - "staging 环境即使 Stripe 回调没真正处理也会返回 200，真实状态要去 payment_events 表查"
- **"不要做"清单**：冲着 agent 默认行为纠偏。如"不要默认用 Inter 字体""不要动不动紫色渐变"。
- **具体可执行的工作流**：每步写清"做什么 + 用什么工具/命令"。
- **硬性规则**：用"必须/绝不/禁止"，不用"建议/可以考虑"。

### 不该写的（纯噪声）

- 显而易见的事："写完代码后要运行测试"——agent 本来就会。
- 教程式解释：那是 references/ 的职责。
- 临时状态：那是记忆的职责。

### 持续攒坑点

每次 agent 用这个 skill 又栽进新坑，回头把坑补进 Gotchas。skill 越用越准。

### 别把 agent 锁死（avoid railroading）

步骤不要写得太死。agent 对指令服从度高，写太死遇到没覆盖的情况会僵在轨道上硬开。正确姿势：**把需要的信息给足，把怎么走的自由留给 agent**。

## 四、9 类 skill 分类参考

来自 Anthropic 内部几百个 skill 的归类。最好的 skill 干干净净落在某一类里；想一次干太多事、横跨好几类的 skill 反而把 agent 搞糊涂。

| 类别 | 干什么 | 例子 |
|------|--------|------|
| 库和 API 参考 | 教 agent 正确用某个库/CLI | 内部计费库的边界情况和坑 |
| **产品验证** | 教 agent 怎么测试自己写的代码 | 无头浏览器跑注册流程并逐步断言 |
| 数据查询分析 | 连接数据和监控系统 | 该 join 哪些表看转化漏斗 |
| 业务流程自动化 | 把重复工作流压成一条命令 | 聚合工单和 PR 生成站会日报 |
| 代码脚手架 | 按团队规范生成样板代码 | 新建预接好鉴权和日志的应用 |
| 代码质量与审查 | 强制执行代码质量 | 全新视角子 agent 做对抗式审查 |
| CI/CD 与部署 | 拉取推送部署代码 | 盯 PR 重试不稳定 CI、解决冲突 |
| Runbook 排障手册 | 从报警症状做多工具排查 | 给请求 ID 把所有系统日志拉齐 |
| 基础设施运维 | 带护栏的例行维护 | 清理孤儿资源前先发确认 |

> **如果只做一类，先做验证类**——Anthropic 实测对 agent 输出质量提升最明显。

## 五、SKILL.md 模板

```markdown
---
name: my-skill
description: >
  当用户要 [具体触发场景] 时使用。覆盖关键词：[关键词1]、[关键词2]。
  （≤250 字符，写给模型看的触发条件，不是给人看的摘要）
---

# My Skill (my_skill_id)

## 触发词
关键词1、关键词2、关键词3

## 概述
一句话说清这个 skill 干什么、什么时候该用。

## 前置条件
- 依赖什么环境/工具/文件

## 工作流
1. [步骤1]：具体操作 + 对应的工具/命令
2. [步骤2]：...
3. [步骤3]：...

## 坑点清单（Gotchas）★ 含金量最高
- [agent 推断不出来的坑 1]
- [agent 推断不出来的坑 2]
- [字段命名不一致 / 环境差异 / 隐藏副作用 ...]

## 关键规则
- 必须/绝不/禁止 的硬性约束

## 不要做
- [冲着 agent 默认行为纠偏的"不要"清单]

## 输入/输出
- 输入：input/xxx/
- 输出：output/xxx/

## 参考（按需查阅）
- references/api.md — 详细 API 参数
- references/troubleshooting.md — 排查手册
- scripts/smoke_test.sh — 冒烟测试
```

## 六、反模式

1. **写教程**：把"你可以这样做"改成"这样做"。
2. **模糊描述**：把"适当处理错误"改成"出错重试 3 次，仍失败则跳过并记录到 errors.json"。
3. **遗漏安全规则**：涉及删除/发布/部署必须写确认流程。
4. **硬编码路径**：用占位符或读配置，不写死绝对路径。
5. **忘更新索引**：新增/修改 skill 后必须同步 `_index.md`。
6. **description 写成摘要**：要写触发条件，不是功能介绍。
7. **正文写 agent 本来就会的**：只写增量信息，删掉显而易见的内容。
8. **步骤锁死**：给信息，不要锁死走法。

---

## 七、高阶玩法（按需）

- **记忆**：skill 在 `.agents/memory/` 下维护执行历史（如日报 skill 记录上次推送内容，下次只报增量）。
- **脚本**：把取数/清洗/校验等底层活封装成 `scripts/` 里的函数，agent 只管编排，不重复造轮子。
- **首次使用引导**：需用户配置的 skill，存 `assets/config.json`，首次运行检测配置缺失则主动询问用户并写入。

> 这三招让 skill 从"一份好文档"升级为"带记忆、带工具、带保险丝的小型工作系统"。
