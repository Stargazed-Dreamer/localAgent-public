# 编码行为准则

> AI agent 在写代码前/写代码中/改代码时必须遵守的行为约束。
> 来源：Karpathy 四原则（Think Before / Simplicity / Surgical / Goal-Driven）+ Ponytail 7 级决策阶梯。
> AGENTS.md 顶部"编码前必读"引用本文件。

---

## 一、写代码之前：Think Before Coding

**不要假设。不要藏起困惑。把权衡摆到明面上。**

动手实现前：
- 把假设**显式说出来**。不确定就问，不要猜。
- 存在多种合理解读时，把它们**列出来**让用户选，不要默默挑一个。
- 有更简单的做法时，**主动指出并推回**，哪怕和用户说的方向不同。
- 某处不清楚时，**停下来**，说清哪里不清楚，再问。

> 反模式：用户说"加个登录"，agent 默认选了 JWT + Redis session + 邮箱验证，一路写到底。正确做法是先问清"会话存储用哪种、要不要第三方登录、密码策略是什么"。

## 二、写多少代码：Ponytail 7 级决策阶梯

**最该写的代码，是从没被写出来的那行。** Lazy = 高效，不是偷懒。

在**理解问题之后**（读完任务、追踪了真实数据流），从上往下停在第 1 个成立的台阶：

1. **这事根本不用做吗？**（YAGNI）→ 不做。多数"未来可能需要"的功能现在都不需要。
2. **代码库里已经有了吗？** → 复用已有的 helper/util/模式，不要重写。
3. **标准库已经能做了吗？** → 用标准库。
4. **平台原生特性覆盖了吗？** → 用平台特性。
5. **已装的依赖能解决吗？** → 用已装依赖，不引新依赖。
6. **能一行写完吗？** → 写一行。
7. **都不行，才写最少能跑的代码。**

> 阶梯在理解问题**之后**跑，不是代替理解。一个你不懂的小 diff，只是披着高效外衣的偷懒。

### 规则

- 不写没被明确要求的抽象。
- 能不引新依赖就不引。
- 不写没人要的样板。
- **删除优先于新增。无聊胜过聪明。文件越少越好。**
- 最短能跑的 diff 赢——但前提是你理解了问题。在错误的地方做最小改动，不是 lazy，是第二个 bug。
- 复杂请求要反问："你真的需要 X，还是 Y 就够了？"
- 两个标准库方案行数相同时，选边界情况更正确的那个。lazy 指的是更少代码，不是更脆弱的算法。
- **有意简化的地方用 `ponytail:` 注释标记天花板**：如 `ponytail: 这里用 O(n²) 扫描，n<100 可接受；超过则改为哈希索引`。注释要说清天花板和升级路径。

## 三、怎么改代码：Surgical Changes

**只动该动的。只收拾自己造成的烂摊子。**

改已有代码时：
- 不要"顺手优化"相邻的代码、注释、格式。
- 不要重构没坏的东西。
- 匹配现有风格，哪怕你会换种写法。
- 发现无关的死代码，**提一句**，不要删。

你的改动产生的孤儿：
- 删除**你的改动**导致的未使用 import/变量/函数。
- 不要删**既有的**死代码，除非被要求。

> 检验标准：每一行改动都能直接追溯到用户的请求。

---

## 四、怎么算完成：Goal-Driven Execution

**定义成功标准。循环验证直到达标。**

把祈使句任务转成可验证目标：

| 不要写成 | 改成 |
|---------|------|
| "加个校验" | "为非法输入写测试，然后让它们通过" |
| "修这个 bug" | "写一个能复现 bug 的测试，然后让它通过" |
| "重构 X" | "确保改前改后测试都通过" |

多步任务先报一个简短计划：
```
1. [步骤] → 验证：[检查方式]
2. [步骤] → 验证：[检查方式]
3. [步骤] → 验证：[检查方式]
```

强的成功标准让你能独立循环到底；弱的标准（"能跑就行"）会不断回头确认。

## 五、不能偷懒的区域

> Lazy 指的是更少代码，不是省掉该做的事。

以下区域**必须**做到位，不能用"lazy"当借口糊弄：

- **理解问题**：读完任务、追踪真实数据流后再选台阶。不懂的小 diff = 假高效。
- **信任边界的输入校验**：外部输入（用户/API/文件）必须校验。
- **防数据丢失的错误处理**：写文件/删数据/迁移前要有保护。
- **安全**：注入、越权、密钥泄露。
- **可访问性**（如项目有此要求）。
- **真实硬件的校准**：平台不是理想规范，时钟会漂、传感器会偏。
- **任何被明确要求的事**。

### 留一个可运行的检查

非平凡逻辑要留**一个**能跑的检查——逻辑坏了就失败的最小东西（一个 assert 演示或一个小测试文件；不要框架、不要 fixture）。一次性的一行代码不需要测试。

---

## 速查（agent 每次写代码前过一遍）

- [ ] 我的假设说出口了吗？不确定的问了吗？
- [ ] 7 级阶梯跑了吗？是不是本来不用写？
- [ ] 改动是否每一行都追溯到用户请求？
- [ ] 成功标准是什么？怎么验证完成？
- [ ] 信任边界/数据丢失/安全这几处做到位了吗？
- [ ] 非平凡逻辑留了可运行的检查吗？
